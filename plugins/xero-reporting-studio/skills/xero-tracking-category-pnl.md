# Profit and Loss by Tracking Category

Use `list_tracking_categories` (`TrackingCategories[].TrackingCategoryID`, `.Options[].TrackingOptionID`) to resolve the category and option names the user names (e.g. "Department: North") to their IDs — never guess or type an ID. Call `get_profit_and_loss` with `trackingCategoryID` / `trackingOptionID` (and, for a second dimension, `trackingCategoryID2` / `trackingOptionID2` — P&L only) alongside `fromDate`, `toDate`, `standardLayout`, `paymentsOnly`, exactly as the Profit and Loss (P06) skill does. `get_balance_sheet` only accepts `trackingOptionID1` / `trackingOptionID2` (no category-ID params at all) — offer a tracking-filtered Balance Sheet only if the user asks, filtered by option only, and say so plainly.

This is a written specification, not a kit report: the shared report kit's input roles (`start`, `end`, `asAt`, `basis`, `cmp*`, `org`, `persona`, `display`) have no slot for a tracking-dimension picker, so build this report's controls and rendering directly rather than assembling it on `{{KIT}}`/`{{CFG}}`. Reuse the Profit and Loss (P06) skill's statement layout, KPI cards, income-to-net-profit view and validation logic, scoped to the chosen option(s), plus a header line naming the category and option(s) actually queried (never the raw IDs). When two dimensions are set, also offer an "All options" comparison view: one `get_profit_and_loss` call per option value in the first dimension (bounded, e.g. the category's first 12 options; state the cap), tabulated side by side — never inferred by splitting a single filtered call.

Validate exactly as P06 for the filtered result (every section total = Σ its account rows; Gross Profit and Net Profit formulas), plus: in the "All options" view, the sum of every option's Net Profit is an information-only figure against the unfiltered organisation-wide P&L for the same dates — Xero's tracking totals can double-count untracked or multi-tracked transactions, so this is disclosed as information, never Pass/Fail.
## Interactivity

Declare `from_date` / `to_date` (date) mapped 1:1 to `get_profit_and_loss`'s `fromDate` / `toDate`, `basis` per the foundation's basis pattern (two bindings, `paymentsOnly` static `false` / `true`), `tracking_category_id` and `tracking_option_id` (string, holding IDs — never an enum "populated from" categories; filled client-side from a `list_tracking_categories` binding) mapped 1:1 to `trackingCategoryID` / `trackingOptionID`, and — only when a second dimension is requested — `tracking_category_id_2` / `tracking_option_id_2` mapped to `trackingCategoryID2` / `trackingOptionID2`. `standardLayout` is static `true` on every binding. Plus `organisation` per the foundation — that is 8 inputs at the platform cap when both dimensions are declared; drop the second dimension's inputs entirely (not just leave them blank) when the user asks for one dimension only. The "All options" fan-out is bounded client-side `getData` calls per the foundation's fan-out rule, never `setInputs`.

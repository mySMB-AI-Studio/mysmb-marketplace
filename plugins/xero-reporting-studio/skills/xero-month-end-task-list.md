# Month-End Task List

Review, don't reconcile automatically: pull live figures across bank/cash, receivables, payables, payroll, journals, GST and balance-sheet areas from `xero-accounting`, `xero-payroll-au` and `xero-assets`, and turn each area's live state into ONE categorised task list — never post, correct or close anything. Cross-connector note: `xero-payroll-au` and `xero-assets` are SEPARATE MCP connectors from `xero-accounting` (confirmed tool names below come from each plugin's own README, not from the foundation file, and their exact param schemas were not exercised live) — treat every payroll/asset finding as informational until checked directly in Xero.

Per area:
- **Bank and cash** — `get_bank_summary` for the period: an account whose Closing balance is negative is Required to review. This skill does not call `list_bank_transactions` itself; point to the Bank Reconciliation Status skill for unreconciled-item detail (Review).
- **Receivables** — `list_invoices` (`where: Type=="ACCREC"`, `statuses: AUTHORISED`, paged per the foundation) aggregated the same way as Aged Receivables: an invoice more than 90 days overdue is Required to review; a rising overdue total versus the prior month, when the user supplies that figure, is Review.
- **Payables** — the same method with `Type=="ACCPAY"`: a bill overdue or due within the next few days is Required; supplier concentration is Review.
- **Payroll** — `list_pay_runs` (`xero-payroll-au`): a pay run for the period still in a draft-like status close to the period end is Required; `get_pay_run` on the latest run for its status detail. `list_timesheets` (`xero-payroll-au`): unapproved timesheets for the period are Review. Only the tool names `list_pay_runs`, `get_pay_run`, `list_employees` and `list_timesheets` are confirmed (from the Xero Payroll AU plugin's own tool list) — their parameters were not verified live, so map cautiously and confirm the real param names during the discovery call before wiring a binding.
- **Journals** — `list_manual_journals` (`where`, `order`, `page`): take the period's journals client-side on `Date` (period_start to period_end), skipping `VOIDED` and `DELETED`. A `DRAFT` manual journal dated in the period is Required (post it or delete it before close). A `POSTED` journal with any line of $10,000 or more, or a round-thousand amount, is Review; cite its date, narration and amount. Do NOT use `list_journals` for this area: it needs a journals scope this connector does not hold and always fails as unauthorised. If `list_manual_journals` itself errors, show one Information-required task ("Manual journals for the period — confirm directly in Xero") rather than silently skipping the area.
- **GST** — `get_balance_sheet` (GST account balance) at the period end, shown alongside — never recomputed against — the accrual movement the GST Reconciliation Detail skill computes; if the two might differ materially, the task is Required: run that skill.
- **Balance-sheet housekeeping** — `get_balance_sheet`: any Suspense, Uncategorised or clearing-style account with a non-zero balance is Required to clear. `list_assets` (`xero-assets`) confirms the fixed-asset register looks current (count, and last-modified where the tool returns it) — **there is no tool to post a depreciation journal on this connector**; a stale-looking register or an unposted month's depreciation is always an Information-required task for the bookkeeper to action directly in Xero, never something this skill claims to do itself.

Categorise every finding as **Required** (an objective check failed against live data — negative bank balance, a draft pay run near period end, a non-zero suspense account), **Review** (a live figure exists but needs human judgement — ageing concentration, unusual journals), **Information-required** (this connector genuinely cannot answer it — for example whether a depreciation journal has been posted), or **Optional** (good practice, not close-blocking). State this rule plainly in the output so a reader can see why each task landed where it did.

Validate that every Required/Review task cites the specific figure and threshold that produced it — never an unsupported judgement call — and that Information-required tasks are exactly the ones this connector cannot answer, never a catch-all for something merely inconvenient to check.
## Interactivity

Declare `period_end` (date, default `"today"`) mapped 1:1 to every `xero-accounting` binding that takes a single `date` (the GST/suspense `get_balance_sheet` call), `period_start` (date) mapped to `get_bank_summary`'s `fromDate` (with `toDate` = `period_end`), `page` (number) per the foundation's paging rule for the `list_invoices` bindings, and `organisation` per the foundation, sent as `xero_tenant_id` on every `xero-accounting` binding — `xero-payroll-au` and `xero-assets` bindings are on a separate connection and are not organisation-scoped the same way; say so if they return data for a different org than the one selected. A specific pay run is an entity picker (a string input holding its ID, filled client-side from `list_pay_runs`), never an enum "populated from" pay runs. Task-category filter and the checklist's expand/collapse are client-side.

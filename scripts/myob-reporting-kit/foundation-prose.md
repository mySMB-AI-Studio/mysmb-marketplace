Resolve the MYOB company file, period or as-at date, and accounting basis (`Accrual` or `Cash`, where the underlying tool takes `reporting_basis`) — but prefer declaring them as report inputs with sensible defaults over asking the user up front; ask only when a required choice genuinely cannot be defaulted. Do not ask for an output format: every report is a single self-contained HTML document saved through artifact_save with a .html filename.

Before starting any report, confirm the tool it needs actually exists in the current myob-accounting connector (see "Connector facts" below). Payroll, inventory, jobs, timesheets, budgets and bank-feed reports all have real tools. What the connector does NOT have: a jobs list, a trial-balance report, a cash-flow report, an account register, or company preferences. If the data isn't exposed, say so plainly and suggest a MYOB export as a fallback — never approximate a report from adjacent data just because the real tool is missing.

Use the connected MYOB tools for live data. Never invent, estimate, silently substitute, or reuse illustrative workbook values. Mark unavailable figures N/A — not in source — and include a Sources & limitations section naming tool calls, report dates, basis, and assumptions explicitly approved by the user.

Perform every tie-out required by the report skill. Show a compact Validation section with each equation and Pass/Fail. If a material check fails, explain the discrepancy prominently. **A check is Pass only when every figure it uses was actually returned.** A check computed from missing, errored, truncated or empty data renders N/A (or Fail when the missing data is itself the problem) — never Pass. Compare money with a tolerance of 0.01 everywhere (`Math.abs(a - b) < 0.01`): the connector does not round intermediate totals.

### Connector facts (myob-accounting)

* **Company file:** every tool except `list_company_files` and `list_tax_codes` accepts an optional `myob_company_file_id` that targets that company file for the call. `list_company_files` lists the files.
* **Errors arrive as data:** a failed tool call returns `{ "__error": "<message>" }` as the binding's normal data — not only as `bundle.errors[id]`. See the error contract below.
* **UID params are validated as UUIDs.** An empty string `""` fails the call. To mean "all", omit the param.
* **Profit and loss:** `get_profit_and_loss` and `get_profit_and_loss_3m` take `from_date` and `to_date` (both required) and `reporting_basis` (`Accrual` | `Cash`). They return `AccountsBreakdown[{ Account{UID, Name, DisplayID}, AccountTotal }]` with **no totals and no classification** — add a `list_accounts` binding, join on `Account.UID`, and sum per `Classification` yourself. The Australian financial year runs 1 July – 30 June. Any range that may cross 1 July (FY comparisons, rolling 12 months, any reader-editable range) must use `get_profit_and_loss_3m`, which splits at 1 July and merges.
* **Balance sheet:** `get_balance_sheet` takes `date` (required — not `as_of_date`) and `reporting_basis`.
* **Accounts:** `list_accounts` takes `type` (MYOB account Type: `Bank`, `AccountReceivable`, `OtherCurrentAsset`, `FixedAsset`, `OtherAsset`, `CreditCard`, `AccountsPayable`, `OtherCurrentLiability`, `LongTermLiability`, `OtherLiability`, `Equity`, `Income`, `CostOfSales`, `Expense`, `OtherIncome`, `OtherExpense`), `classification` (`Asset`, `Liability`, `Equity`, `Income`, `CostOfSales`, `Expense`, `OtherIncome`, `OtherExpense` — no spaces) and `is_active`. No paging and no date: `CurrentBalance` is today's balance only. Rows carry `UID`, `DisplayID`, `Name`, `Type`, `Classification`, `IsHeader`, `CurrentBalance`. Exclude `IsHeader: true` accounts from every sum.
* **Invoices and bills:** `list_invoices` / `list_bills` take `status` (`Open` | `Closed` | `All`, default `Open`), `customer_uid` / `supplier_uid`, `from_date`, `to_date`, and page args; `page_index: 0` fetches every page. The outstanding amount is `BalanceDueAmount`; the document value is `TotalAmount`.
* **Single-page lists:** `list_contacts`, `list_payments` and `list_supplier_payments` return ONE page only. Pass `page_size: 1000` (the maximum). If exactly 1000 rows come back, show a "may be truncated" warning and never mark a completeness check Pass. `list_payments` filters by `contact_uid` (not `customer_uid`).
* **Ageing:** `get_aged_receivables` / `get_aged_payables` take `report_date` and `contact_uid`. Balances and open status are always as of TODAY; `report_date` only changes days-overdue bucketing. When `report_date` isn't today, say so in a visible banner.
* **Journal:** `list_journal_transactions` takes `from_date`, `to_date`, `account_uid`, `job_uid`, `page_size` (≤5000) and fetches everything. The account/job filters keep a whole transaction when ANY line matches — filter `Lines[]` client-side to show only the matching lines. `Amount` is always positive; `IsCredit` gives the side.
* **Payroll:** `get_employee_payroll_advice` REQUIRES `employee_uid`. MYOB ignores the dates, so the connector filters advices by pay-period overlap with `from_date`/`to_date` itself — one call returns every advice in range for that employee. Reports that cover many employees use a fan-out loop (below).
* **Jobs:** `list_job_register` takes only `job_uid` and page args — no date, year or month params. Rows are `{ Job, Account, Year, Month, Activity, YearEndActivity }`; filter the period client-side. `Year` may be the financial year rather than the calendar year — verify on first run. There is no `list_jobs`: discover job UIDs from `list_job_register` rows or journal `Lines[].Job`.
* **Budgets:** `get_budget` takes `financial_year` as an integer (2027 = FY2026-27), current or next FY only.

### Error contract

In `onData` and after every `getData` call, treat a source as FAILED when either `bundle.errors[id]` is set (codes `tool_error`, `invalid_inputs`, `tool_not_found`, `connection_unavailable`, `needs_connection`) or the returned data carries `__error` (`data[id].__error`). Write one helper and use it for every section. For a failed source:

* Show the message in that section (for `needs_connection`, say this viewer has not connected MYOB — offer nothing else).
* Never render $0, an empty table, or "no items" as if it were real data.
* Mark every check that uses it N/A or Fail — never Pass.
* Keep rendering every other section.

### Live reports (the default)

A report over connected MYOB data is LIVE: never bake retrieved rows or computed figures into the HTML. Pass dataBindings to artifact_save and write the document to render everything from hydrated data through the injected MyHubReport SDK. The platform injects the SDK at serve time — never include, stub, or fetch it yourself.

* Declare one binding per MYOB dataset the report shows, targeting the myob-accounting MCP server's tools, e.g. `{ "id": "profit_and_loss", "tool": { "mcp": "myob-accounting", "name": "get_profit_and_loss_3m" }, "params": { "from_date": { "kind": "input", "input": "from_date" }, "to_date": { "kind": "input", "input": "to_date" }, "reporting_basis": { "kind": "input", "input": "basis" }, "myob_company_file_id": { "kind": "input", "input": "company_file" } } }`. Param kinds: `{"kind":"static","value":…}` for choices fixed at authoring, `{"kind":"context","source":"now.date"}` for today (the only context value), `{"kind":"input","input":"…"}` for anything a reader may change.
* **Limits:** at most 8 declared inputs and 12 bindings. Input types are `string`, `date`, `enum`, `number`, `boolean`. Every binding id must be read somewhere in the HTML.
* **Typed parameters (the connector validates types and rejects the whole call):** a boolean tool parameter (`is_active`, `order_desc`) is either a static JSON boolean (`{ "kind": "static", "value": true }`) or bound to a declared `boolean` input — never an `enum` or `string` input, which sends `"true"` and fails with "Expected boolean, received string". A number parameter (`page_size`, `page_index`, `financial_year`) is a static JSON number or a `number` input. An "active only / all" choice for the reader is a client-side filter over one binding that omits `is_active` — never a re-query that sends `is_active: false` (that returns only inactive records).
* Declare inputs for the report's controls instead of interrogating the user:
  * `company_file` — a `string` input holding the company file id, defaulting to the file in play. Bind it to `myob_company_file_id` on EVERY binding except `list_company_files` and `list_tax_codes`. When `list_company_files` shows more than one file, add a `company_files` binding to `list_company_files` and fill a header selector from it client-side. The header must show the name of the file actually queried (looked up from the current `company_file` value), never a hardcoded label.
  * Date range / as-at — declare date inputs that map 1:1 onto the tool's REAL date parameters (`from_date`, `to_date`, `date`, `report_date`). Period presets (this month, last quarter, FY to date) are a CLIENT-SIDE picker that computes and sets the declared date inputs — never an input of their own.
  * `basis` — only when the tool takes `reporting_basis`: an `enum` input with options exactly `Accrual` and `Cash` (default `Accrual`), mapped 1:1.
  * The report skill names which of these (and any report-specific inputs) apply.
* **Enum inputs** hold 1–12 options fixed at authoring; values outside them are rejected. Use enums only for genuinely fixed choices (basis, status, detail level, persona, Customer/Supplier/All). Never declare an enum "populated from" `list_accounts`, customers, suppliers, items, employees or jobs.
* **Entity pickers** (account, customer, supplier, item, employee, job): declare a `string` input (maxLength 36) holding the UID, and fill its dropdown client-side from a list binding (`list_accounts`, `list_contacts`, `list_items`, `list_employees`, `list_job_register` rows, or rows the report already has). For "all", the call must OMIT the UID param — either filter client-side over an unfiltered binding, or declare a second, filtered binding that you only call with `getData` once a real UID is chosen. Never pass `""`. A required picker defaults to a real UID found during generation.
* **Multi-select** doesn't exist as an input type. Use client-side selection over one unfiltered binding, or a `string` input of comma-separated UIDs parsed client-side.
* **Relative dates:** a date input's default is either fixed or today. For month-to-date, FY-to-date or "last month", compute the dates client-side on load, then re-query with `MyHubReport.getData(id, inputs)` and call `MyHubReport.setInputs(...)` so the view and the share link agree. Skip the re-query in snapshot mode.
* **Fan-out:** when a tool needs one call per entity (for example `get_employee_payroll_advice` per employee), declare ONE binding whose UID param maps a `string` input, and loop client-side with `await MyHubReport.getData(id, { ...inputs, employee: uid })` over the list binding's rows. Keep the loop bounded (state the cap, e.g. 50 entities, and say so in the report when it's hit), show progress, and disclose the loop in Sources & limitations. Snapshots keep only the bundle data, so results fetched by the loop aren't frozen — in snapshot mode say which sections need the live report.
* **THE MAPPING LAW:** every declared input is EITHER a bound input — consumed by at least one binding param, each param mapping ONE declared input (or static/context value) onto ONE parameter the tool actually accepts — OR a presentation input. Presentation inputs (`persona`, `detail_level`, client-side filters such as a minimum days-overdue, a fund filter or a text filter) are allowed: declare them, but do not bind them to any param; they never trigger a re-query and still count toward the 8-input limit. Declare nothing that is neither. Discover the tool's real parameters during generation. The keys passed to `MyHubReport.getData(...)` and `MyHubReport.setInputs(...)` are the DECLARED INPUT NAMES exactly as written in inputs — never the tool's parameter names.
* During the generation turn call each tool ONCE to learn its response shape, then write mapping and rendering JavaScript against that shape. Do not paste the discovered values into the document.
* Render from `MyHubReport.onData(bundle => …)`: read `bundle.data[bindingId]` per section and apply the error contract above. Show a loading skeleton until the first bundle arrives; never a permanently empty section.
* When a control changes, re-query just that data with `MyHubReport.getData(bindingId, { input: value })` and re-render the affected sections. Call `MyHubReport.setInputs({...})` on every control change so downloads and share links capture the reader's current view.
* Interactivity that does NOT need new data is client-side JavaScript over already-hydrated data — column sorting, a text filter on any long table, tab/segment switches. Never add a binding for sorting, filtering, or aggregation of data you already have.
* Recompute the Validation section's tie-outs in JavaScript on every hydration, against the numbers actually rendered.
* **Snapshot mode:** when `MyHubReport.mode === 'snapshot'` (downloads and share links serve frozen data), disable or hide controls that would re-query, keep client-side sorting/filtering working against the embedded data, and state clearly that figures are frozen as of the captured time.
* Data freshness in the header comes from `bundle.fetchedAt`, never the generation timestamp.

Reserve a STATIC report (no dataBindings, data baked in) for the one case it is right: the user explicitly wants a frozen, point-in-time analysis. Then pass `connectors: ["myob-accounting"]` to `artifact_save` so the library still shows the data source.

### Consistent visual system

Build accessible semantic HTML with all CSS and optional lightweight JavaScript inline; do not fetch external libraries. Use MYOB's real brand palette (sourced from MYOB's official Logo Usage Guide, developer.myob.com — not an AI-generated guess): primary `--accent:#5c247b`; secondaries `--yellow:#eab80f`, `--orange:#ec6915`, `--green:#76ad1c`, `--teal:#009699`, `--blue:#2aabe1`; ink tints `--ink-80:#333333`, `--ink-50:#7f7f7f`, `--ink-30:#b3b3b3`, `--ink-10:#e6e6e6`. MYOB's guide defines no red/danger color — use `--neg:#ec6915` (the orange) as the negative/overdue/failing-check color, a project judgment call, not a verified MYOB brand color. Use a responsive 12-column card grid, 8px spacing rhythm, system sans-serif, strong hierarchy, tabular numerals, bracketed negatives, and clear print styles. Prefer SVG/CSS charts with legends and accessible labels; charts re-render from hydrated data like every other section. Tables need sticky headers when useful, right-aligned numbers, visible totals, sortable columns, and horizontal overflow on small screens. Render input controls (company file selector, period picker, basis toggle, persona) as a compact control row in the header area, styled with the same system.

**Dark mode:** define every colour as a CSS custom property on `:root` and override them under `:root[data-myhub-theme='dark']` (background, surface, text, borders, muted text, chart colours). The host sets that attribute; never use `prefers-color-scheme`.

The header must show report name, company file (the one actually queried), period, basis, and data freshness (from `bundle.fetchedAt`). Add an executive summary, then detail, validation, and sources. Save the final document with `artifact_save`; do not paste HTML into chat.

### Persona modes

Every report declares a `persona` presentation input (not consumed by any data binding — it only controls rendering) with options `Client`, `Bookkeeper`, `Practitioner`, `Executive`, defaulting to `Bookkeeper`. Render it as a `<select id="personaSel">` in the controls row. `Client` and `Executive` render in **summary mode**: hide elements classed `detail-block` (line-item tables, per-transaction breakdowns) and show only headline totals, the executive summary, and validation results. `Bookkeeper` and `Practitioner` render in **detail mode**: show everything, including `detail-block` elements. Toggle by setting `document.body.className` to `persona-summary` or `persona-detail` and scoping CSS on those classes (`.persona-summary .detail-block{display:none;} .persona-detail .detail-block{display:block;}`). A failing validation check is never hidden by persona — Pass/Fail always renders regardless of mode. On persona change, call `MyHubReport.setInputs({persona: value})` so downloads/share links capture the reader's chosen mode; this never triggers a re-query since no binding consumes it.
